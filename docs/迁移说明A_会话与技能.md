## A4. 技能 style-distill

### A4.1 它是干什么的
给一张或一组图，**提取/蒸馏画法**并产出可直接粘贴进图生图接口的提示词；也管"改这一张的画风"、
"照这张图的姿态改""结果反复不达标怎么返工"。

### A4.2 七条铁律（违反即失败）【文件核实】

| | 铁律 | 判据 |
|---|---|---|
| R1 | 只迁手法，不迁配色 | 参考图的具体色相/色板不得成为迁移目标；目标图各元素保持自己的色相 |
| R2 | 只搬风格，不搬内容 | 参考图有、目标图没有的东西一律不得挪用 |
| R3 | 不编造 | 看不出就写"未识别（原因）"；不把推测写成事实 |
| R4 | 禁无效词 | 不用"高级感/氛围感强"；每条判断附图中可观察依据 |
| R5 | **负向不是删除键** | 目标图里**已经存在**的大面积显著元素，负向删不掉——必须在投喂前**物理抹掉**，且视觉权重越大越必须擦 |
| R6 | 一轮一个变量 | 一次只改一个模块（姿态/手势/服装/色彩/背景），否则失败无法归因 |
| R7 | 参考组身份会污染 | 参考组同角色时"共同手法"混着该角色身份并会外溢；投喂张数取最少 + 身份特征逐条进负向 |

### A4.3 开工四问【文件核实】

- **Q0 这件事该不该用生成做**：凡能描述成"对现有像素做某个确定变换"的（调浓淡/放大/裁切/拼版/
  加纸纹/改色调）**一律走本地，不调接口**——生成必然重掷脸、姿态、构图
- Q1 投喂图里有没有"不该出现的东西"还没**物理清除**（不是写进负向，是在图上抹掉）
- Q2 这一轮的**唯一变量**是什么（R6）
- Q3 上一次的**失败态**有没有写进负向
- 另：**体积与输出体积预算必须算**（跑 ≥2K 前必报）

### A4.4 标准作业顺序 0→7（顺序不能颠倒）【文件核实】

```
0 输入体检 → 1 定性分析 → 2 人工勾选半风格项 → 3 投喂前预处理（物理擦除）
→ 4 拼提示词（PRESERVE → COLOUR LOCK → STYLE → DO NOT INCLUDE，且必须逐条打开负向词库抄失败态）
→ 5 生成（中间稿一律 1K）→ 5.5 取回结果（独立一步）→ 6 生成后体检 → 7 沉淀失败态
```

其中 **5.5** 的工程结论：生成一拿到 URL 就落盘；**探测式抢档**下载（`curl --speed-limit/--speed-time`，
门槛按**实测区间 20–60 KB/s** 定，不能按理想带宽定）；下完必须 `Image.open().load()` 完整解码校验
（截断文件 `open` 不报错、只有 `load` 报）；多个大文件**串行**取回。

### A4.5 提示词骨架与负向【文件核实】

六块固定顺序：`HEAD（总纲+身份声明）→ PRESERVE 🔒 → COLOUR LOCK → POSE（仅姿态档位）→ STYLE → DO NOT INCLUDE`；
负向分两层：**必含的固定守卫**（色相/去色/调色板守卫词）+ **本轮失败态**（从 `negative-library.md` 逐条抄）。

### A4.6 体积预算（实测数字）

- 上限：**1.96 MiB 通过 / 2.12 MiB 起被拒**（`400 form field too large or incomplete`）【实测】
- 投喂体积由**目标尺寸**决定、与源图分辨率无关（把参考缩到 320px，归一化到 4K 后仍要 1.51 MiB）【实测】
- **JPEG 投喂比 PNG 小约 5 倍**：同尺寸同两张图 PNG 2.80 MiB → JPEG q88 0.56 MiB；
  "喂前本地降熵"几乎无效（投喂前会把图放大回目标尺寸，而 PNG 无损）【实测】
- 输出体积→取回时间：1K≈2MB｜2K≈4MB｜4K≈10MB；CDN 实测 **0.2–97 KB/s**（约 200 倍抖动），
  且结果域名会在**多个网关间轮换**【实测】

### A4.8 两条工程纪律（用血换来的）【实测】

1. **命令一律写成脚本文件，不要内联**：PowerShell 不支持 `<<` 重定向；中文与嵌套引号会让
   `python -c "..."` 反复失败（本会话内联引号事故 ≥8 次；其中一次把 `#` 注释写进字符串，
   直接产出非法 JS）。**正确做法**：写 `.py`/`.ps1` 文件再执行。
2. **改任何 `.py` 前先 `compile()`**：把 UTF-8 前置写在 `from __future__` 之前这个错，本会话犯了 3 次。

## A6. 局部改图的配方（本会话最实用的一条）

- 只发 `--mask`（会连干净原图一起发）时，模型**照抄原图把那块"恢复"** → 近原图返回
- **`--mask --mask-primary`**（把涂红图当主图、不发干净原图）→ **真的重画**：
  实测黑色蝴蝶结一次画成，蒙版内改动 >120 的像素占 25%；**2/2 复现**（两版平均差仅 3.79）
- 代价：① 整图被轻微微调（均值约 5/255，**不是逐像素保护**）；
  ② 加了 primary 后走 `b64` 响应路线，**该路线不守 `size`**（3/3：请求 1024×1024 回 1254×1254）
- 机制解释保留残余不确定：两次成功同时走了 `b64` 路线，故"载荷形状"与"响应路线"**未完全分离**

## A10. 2026-09-25 追加：残留目录的清除（R12 结案）

**做了什么**：`style-distill/_backup_comfyui_removal/`（36 文件＝27 个被 git 跟踪 + 9 个未跟踪）
从**全部历史**中剥离，磁盘副本一并删除。

**为什么不是只改注释**：`git rm --cached` 只停止未来跟踪，内容仍在历史与任何克隆里，
达不到 `.gitignore` 注释宣称的"保持仓库中无该内容"；故按用户决定走重写。

**做法与对账**【实测】：

1. **仓库外全量安全备份**（重写前必做）：`git bundle create <file> --all`（6.11 MB）
   ＋ 该目录 36 文件副本 → `Desktop\mantu_rewrite_backup_20260925_110102\`。
   恢复方式：`git clone <该目录>/mantu_all_refs.bundle <新目录>`。
2. `git filter-branch --force --index-filter "git rm -r --cached --ignore-unmatch -- '<路径>'" --prune-empty -- --all`
   → 提交数仍是 **38**（无提交被剪掉；该目录只在一次提交里被加入，故无空提交产生）。
3. 删 `refs/original` → `reflog expire --expire=now --all` → `gc --prune=now`（不删这三样，旧对象仍可及）。
4. **对账**：排除该路径后，新旧 HEAD 的 `git diff --stat` **为空**（其余内容逐字节未变）；
