# 风格蒸馏 · 图生图

## 何时用

本技能负责语义层：任务分类、输入图角色分配、风格/姿态分析、提示词编译、失败归因与返工决策；已确定的生成提交交给 ZCode 的 `image-edit` 执行层。确定性像素处理不走本技能的生成路径；复杂多图任务可使用只读分析子代理，但不得由子代理提交或重试真实请求。

- 给一张图或一组同风格图，要**提取／蒸馏**出一种画法，产出可直接粘贴进图生图接口的提示词。
- 给一张要改的图，要**改它的画风**（保内容与配色）。
- 给一张**姿态参考图**，要照它的姿态改目标图（定点姿态迁移）。
- 图生图结果反复不达标（手势画不对、该消失的物体反复回来、颜色被带跑），要诊断与返工。

## 七条铁律（违反即失败）

| | 铁律 | 判据 |
|---|---|---|
| R1 | **只迁手法，不迁配色** | 参考图的具体色相、色板、hex 不得成为迁移目标；目标图每个元素保持自己的色相，暗部与高光从该元素自身色相派生 |
| R2 | **只搬风格，不搬内容** | 参考图有、目标图没有的东西一律不得挪用 |
| R3 | **不编造** | 看不出就写"未识别（原因）"；不得把推测的作者、年代、模型、镜头参数、制作流程写成事实；不得声称能还原原提示词 |
| R4 | **禁无效词** | 不用"高级感／氛围感强／质感高级"；每条判断必须附图中可观察到的依据 |
| R5 | **负向不是删除键** | 负向只对"细碎的、可能新增的"东西有效。目标图里**已经存在**的大面积显著元素，负向词删不掉——必须在投喂前从图上物理抹掉。**该元素在输入图里占的视觉权重越大，越必须物理擦除。** |
| R6 | **一轮一个变量** | 一次生成只改一个模块（姿态／手势／服装／色彩强度／背景）。同轮改两处以上，失败时无法归因 |
| R7 | **参考组身份会污染** | 参考组是同一个角色时，"共同手法"里混着该角色的身份，且当风格图投喂时身份会外溢。投喂张数取最少，并把参考角色的身份特征逐条列进负向拦截 |

## 两条路径：轻量提取 vs 完整蒸馏（选错会烂）

- **单图提取／双图迁移**（撑伞这类任务）：走**轻量路径**——角色表 → 块面观察（STYLE 六行）→
  PRESERVE 逐项锁 → 负向两层 → 1K 一轮。**不跑 10 段模板、不做两轮制**；分析阶段的产出就是 STYLE 六行的观察结果。
- **风格级蒸馏**（≥6 张同风格组）：才走 `references/template.md` 的 10 段模板与两轮制（定性 → 量测 → 填阈值）。
  单图数据撑不起组统计，强行跑只会得到空泛形容词。

判断一句：**投喂参考只有一两张 → 轻量；一组同风格 → 完整。**
（实测 2026-10-06：单图任务硬套感觉词提取，连烧 8 版；改为块面写法后身份全保住。）

## 开工硬规则（2026-10-06 实测版）

**第 0 步：角色表**（发送前核对，不是分析输出）：

| 槽位 | 文件 | 角色 |
|---|---|---|
| image | `<用户原图>` | 身份与颜色唯一来源 |
| image[1] | `<参考图>` | 只提供画法／姿态 |

规则：身份图、画法图、姿态图各自只能有一个来源；角色表里的图必须**全部进入请求**，
`--dry-run` 打印的字段列表与角色表不一致就停止。

- 用户原图是身份源。已生成结果不得回喂为身份图或画法图，**除非用户点名该文件**。
- **用户点名认可的成图是基准资产（2026-10-06 反省，最高优先级）**：用户说某张「对／正确」的那一刻，它就是后续所有轮次的底。后续迭代默认「以它为底做定点修正」（局部重绘 `--mask --mask-primary`、或单变量小改），**从零重掷全图必须先说明理由并获用户同意**。每轮验收的唯一标准是「比基准更好了吗」，不是指标自证。同一失败连续两轮必须停——v5–v8、r9–r14b 连烧十轮没超过 v1，就是这条被绕过的代价。
- **用户没指认的问题不主动修**（2026-10-06 头部事故）：局部重绘只处理用户指认的区域；修 A 区时「发现」B 区有问题，先报告并等用户决定，不自行动手——脸部修复把头改崩的事故即源于此。蒙版不得切在结构（头盖骨／发际线／关节）中间。
- **用户词先消歧。「通透」指干净、透亮、简洁和实体布料，不是透明衣服。**
- **画风迁移默认用 `input_fidelity=low`**（2026-10-06 实测定稿）：单参考图＋全新内容提示词＋edits 请求加 `input_fidelity: "low"`——参考图只取画风不保留内容，一次调用同时达成画风保真与内容全新（`产图/fidelity-low-probe.png`）。此前两段式、裁片引导、草图三段式、本地 ComfyUI 部署全是绕路；任何「按参考图画风画新内容」的任务先试这个参数。
- **任务常量必须正向声明**（2026-10-06 r11 实测）：道具颜色、场景、服装件数要写进正向；负向只拦泄漏，替代不了正向——r11 只在负向禁白伞，结果伞变浅紫灰。
- **全方位模仿含明暗档位**（2026-10-06 r13/r14b 实测）：模板是「深背景压顶＋亮人物」时，LIGHT 段写「人物是画面最亮部分；深色块集中在伞内侧/竹林暗部」，不要把「浅亮」当成本体。汇报与提示词用「身份图／画法图」称呼，不用裸编号——编号叫反会引发用户误解。
- 一轮只改一个变量。同一失败连续两轮后停止改词，先报告原因。
- 禁止居中裁掉脸、发饰或参考主体。预算、比例和字段列表先报，再发送。
- 一次生成 POST。受理状态未知即停止，不自动重试。
- 通道：双图走 `gpt-image-2.5-sunburst`（裸名 `gpt-image-2.5` 实测 404）。Grok 只用于单图，且只走网页引擎路径——
  `run_round.py --model grok-imagine-edit` 只换模型名，仍打 GPT 端点（见 `references/pipeline-notes.md` 通道表）。
  未获用户确认前，不得把两张图拼接成一张。

## 每轮开工前的五问（成本最低、收益最高）

**0. 这件事该不该用生成做？——是「改这一张图」还是「改这一类图」？**
凡是能描述成「对现有像素做某个确定变换」的需求（调浓淡／放大／裁切／拼版／加纸纹／改色调），
**一律走本地像素处理，不调接口**。理由是生成必然重掷脸、姿态、构图，**做不到「其他都不用动」**。
（代价实测：把「把这一张的线稿调淡」交给生成，白烧 3 次生成；把「这一张的 4K」交给生成，
多花一次调用＋近一小时取回，而本地放大 1 分钟就能给、且内容一像素不差。
判据一句话：**需求能否用「对现有像素做某个确定变换」描述出来？能 → 不要生成。**）

1. 投喂图里有没有"不该出现的东西"还没**物理清除**？（不是写进负向，是在图上抹掉）
2. 这一轮的**唯一变量**是什么？（R6）
3. 上一次的**失败态**有没有写进负向？（附 A 词库）
4. **投喂体积与输出体积的预算**算过没有？（见下节「体积预算」；跑 ≥2K 前必报）
5. **同一处失败是不是已经连续两轮？** 是 → 停止改词，走「升级规则」，别再烧第三轮。

## 标准作业顺序

```
0  输入体检      scripts/audit_and_check.py audit
1  定性分析      按 references/template.md 的提示词，输出 0–9 段
2  人工勾选      第 3 段的 🟡 半风格项；不勾 = 按"不迁移"处理
3  投喂前预处理   物理擦除 + 擦除痕迹中和（scripts/erase_region.py）
4  拼提示词      按模板骨架：PRESERVE → COLOUR LOCK → STYLE → DO NOT INCLUDE；
                  **必须打开 references/negative-library.md，把本轮相关的失败态逐条抄进 DO NOT INCLUDE**（词库不会自动生效）
5  生成          先 `--dry-run`：**字段列表＝角色表、比例不裁脸/发饰、投喂 ≤1.96 MiB**，三项核对过再真发；
                 **中间稿一律 1K**（约 2 MB、取回快）；只在最终交付尺寸上跑一次；
                 尺寸跟随目标图；负向用正文替代
5.5 取回结果     **这是独立的一步，不是「生成」的附带动作**（实测取回曾占掉 55 分钟）：
                 · 生成一拿到 URL 就落盘（run_round.py 自动写 round_lib/pending_urls.json）
                 · **探测式抢档**下载：curl --speed-limit/--speed-time，门槛按**实测区间 20–60 KB/s** 定
                   （不能按理想带宽定——门槛过高会把一次平均 61 KB/s 的尝试也杀掉）；
                   **不要把长超时当策略**，低速就立刻断掉重试
                 · 下完**必须** Image.open(p).load() 完整解码校验（**截断文件 open 不报错、只有 load 才报**）
                 · 多个大文件**串行**取回（并行会互抢带宽，实测跌到 1 KB/s）
                 · 补下工具：round_lib/fetch_url.py --pending
6  生成后体检    scripts/audit_and_check.py check；调子剖面用 round_lib/tone_report.py；
                 **风格量化用 scripts/style_metrics.py**（WD14 打标＋调色板，2026-10-06 实测接入）：
                 `python scripts/style_metrics.py <模板图> <产出图>` —— 重合率证画风保真、
                 **笔触密度用 edge 基线出数**（弱/强边缘占比，>图一 40% 即驳杂信号；
                 修正阶梯：组织性约束先行，大简化越界），
                 重合率证画风保真、
                 **Lineart 对照查噪**（生成后提取线稿与模板并排——
                 噪声碎点/驳杂在线稿上呈短碎线，肉眼判读；暗景天然少线需放宽。
                 2026-10-06 实测：首张 probe 即查出发丝区噪声，该手段有检出力）
                 「仅模板/仅产出」清单证内容差异；调色板 top 色号对比证色彩气质。
                 ⚠ 依赖 `pip install wdtagger colorgram.py`，首跑经 HF_ENDPOINT 镜像下载模型（CPU 可跑）
  6.5 交叉验证    **JoyCaption Danbooru 反推 × WD14 交叉**（2026-10-07 试点固化，可选步骤）：
                 `python scripts/joycaption_cross.py <产出图>` —— 第二标签源独立描述同一张图，
                 两源分歧标签即人工复查点（双源一致＝高可信核）。
                 ⚠ 走 HF Space 免费 API（ZeroGPU 配额按窗口恢复，耗尽即 `data: null` error，隔窗重试）；
                 实测同图双源并集比单一源 +35% 标签覆盖。
7  沉淀失败态    把本轮实际出现的失败形态加进 references/negative-library.md
```

**顺序不能颠倒**：第 3 步做不做，结果差别最大。本 skill 的历史里，凡跳过第 3 步直接改提示词的轮次都在原地打转；凡做了第 3 步的轮次，结果方向立刻改变。

## 体积预算（跑 ≥2K 之前必须报的三个数）

| 项 | 实测结论（本轮全程验证） |
|---|---|
| 投喂上限 | **1.96 MiB 通过 / 4.36 MiB 被拒**（400 form field too large or incomplete） |
| 投喂体积由谁决定 | **由目标尺寸决定，与源图分辨率无关**——4K 下把参考缩到 320px，归一化后仍要 1.51 MiB |
| **编码格式是最大杠杆**（2026-09-22 实测） | 同一尺寸同一对图：**PNG 2.80 MiB → JPEG q88 0.56 MiB（约 5 倍）**，且中转站**接受 JPEG 上传**（已跑通）。用 `--encode jpg`，走它就不必经压缩梯子。**"喂前本地降熵"几乎无效**（投喂前会把图放大回目标尺寸，PNG 无损） |
| 省额度的另一种杠杆 | **横向画幅**：2K 横 2048×1152 用「内容灰16＋参考 900px 清晰」只要 1.38 MiB；2K 方要 2.16 MiB |
| 输出体积 → 取回时间 | 1K≈2MB｜2K≈4MB｜4K≈10MB；该 CDN 实测 **0.2–97 KB/s，极差约 200 倍**，且结果 URL 在**多个网关域名间轮换**（同一轮出现过三个不同域名） |

四条规则：
1. **只要放得下就不要压缩投喂**。过度压缩会把身份参考抹糊——那正是「脸不像」的根源
   （实测：参考被压到 448px＋模糊＋量化后脸明显跑偏；改回 900px 清晰、不模糊不量化后立刻变准）。
2. **中间稿一律 1K**；「要更大」优先**本地放大**，而不是再跑一次生成（4K 生成还得把投喂压成二值化）。
3. 要 ≥2K 前先报「**预计多少 MB／预计取回多少分钟／最坏情况**」，由用户决定值不值。
   **工具**：`run_round.py --dry-run` 会自动打印这张报表（投喂体积／是否触发压缩／输出体积／取回时间三档预估），
   **且不会发送**；`--ask` 则是"先报表、再问 (y/N) 确认才发送"（**只适合交互式手跑**，
   agent/后台用 `--dry-run` 即可——读不到输入时会按取消处理，不会误发）。
   跑 ≥2K 之前先跑它——本项目的"4K 跑完下不到"和"身份参考被压糊导致脸不像"两件事，
   都能被这张报表提前拦下。
4. 横向目标会**居中裁切**投喂图 → **投喂图要自己先裁成目标比例**，否则接口的居中裁切会把眼镜、脸切掉。

## 提示词骨架（六块，顺序固定）

0. **FACE 默认段（2026-10-07 用户认可定稿，人像必带）**——eyetest-b 验证帧的五官画法，直接粘贴：
   `脸部画法（低细节水彩）：眼睛是简单的水彩色块——淡青紫色虹膜一抹、深色瞳孔一点、一条上睫毛线；`
   `没有多层渐变，没有高光渲染点；鼻唇两三笔浅色；脸颊有水彩色斑式的光斑；皮肤有水彩留白和微妙的颜色变化。`
   渲染密度是「AI 味」的直接来源（对照实测：渲染脸 15.5% vs 低细节脸 7.9% 弱边缘）——
   特写/开眼人像**必带此段**；渲染式精致五官是本通道的固有倾向，只能靠正向段压制。

1. **HEAD**：总纲与身份声明——"这是一次风格迁移，不是重新设计"；声明哪张图是身份与颜色的唯一来源、哪张只提供手法、哪张只提供姿态。
2. **PRESERVE 🔒**：逐项锁死目标图原有的角色特征、服饰配件、道具、背景、姿势、画幅。带 🔒 的条目是"锁死自有属性"，不是"从参考图迁移"，与被判非 🔵 项的"不迁移"同向。
3. **COLOUR LOCK**：每个元素保持自己的色相；暗部／亮部都从该元素自身色相派生；不得引入参考图的任何色相。
4. **POSE**（仅姿态档位）：身体朝向／头角／肩部／双手位置与朝向／手指关系／体态松紧，逐项写；精细结构用**几何锚点**（位置、朝向、交叉关系、大小、是否靠留白成形），不要只用形容词。
   **方位一律以角色为参照，不要以画面为参照**——写"本子按她自己的方向摆放"而不是"纸面朝向观者"；后者会把物体朝镜头摆正，直接制造出"东西是反的"这类错误（已实测：一句"纸面朝向观者一侧"就让她面前的笔记本反了）。
   **几何锚点必须给"厚度／尺寸"的相对量，不能只给位置或存在性**——写"露出一段**有厚度**的虹膜，明显比上眼睑的线更厚"，而不是"留出一线瞳孔"（已实测：写"一线"，模型就真的只给一条细到没有信息的暗线）。
5. **STYLE**：只讲渲染手法，分行写（LINE / EDGE / COLOUR / HAIR / FABRIC / LIGHT，按需增减 INK / FORM / FACE / SURFACE / SCOPE）。
   每行＝**可观察事实**，禁止「通透／干净／高级」代替观察；看不出就写未识别。
   **标准写法（2026-10-06 定稿，r9 实测后修订）**：
   `LINE：外轮廓细深线，内部无密集排线`｜`EDGE：亮块有清楚边界，不雾成灰白`｜
   `COLOUR：色块内部变化少；阴影＝同一色相加深一档，阴影里不出现冷灰或蓝灰`｜
   `HAIR：大块发色＋少量细丝，不逐缕刻画`｜`FABRIC：衣褶少，转折处一条浅影，布料实体不透明`｜
   `LIGHT：亮来自浅色块与纸色留白，无发光边、无玻璃皮肤`
   （「同色相加深」与负向 `cold grey shading` 要**成对出现**——只写正向，实测阴影仍会落回灰调。）
6. **DO NOT INCLUDE**：把参考图的角色、服饰、道具、场景与一切身份特征逐条列成负向。

## 负向的两层结构

**第一层 · 色彩守卫（固定 7 条，逐字保留）**
`hue shift, recolouring, palette swap, wrong hair colour, colour cast toward a different hue family, monochrome conversion, full greyscale`

**第二层 · 失败态（每轮按实际情况写，全部是可观察的形态）**
从 `references/negative-library.md` 取，并把本轮新发现的形态追加回去。禁止写"不要差""不要崩"这类空话。

两条使用纪律：
- **发色词不进负向**（identity-library 纪律一）：发色由 `wrong hair colour` 与 COLOUR LOCK 守。
- 阴影灰调类（2026-10-06 实测）：结果阴影用冷灰而非同色相加深时，加
  `cold grey shading, grey midtones, desaturated shadows, muddy grey wash`。

两条分流规则：
- 保留目标图背景时**一律剔除** `detailed background / room / scenery` 这类清除词——负向区分不了"不要新增"和"删掉已有的"。
- 目标图自带文字或贴纸时**禁止**出现 `no text / no letters / text-free / no words`。
- **当风格参考本身是无彩色的（黑白漫画、铅笔稿、单色稿）而用户明确要求照搬时**，R1 被显式让出：
  必须把 `monochrome conversion` 与 `full greyscale` **从必含 7 条里移除**（否则正负互斥，结果会卡成半褪色的浑浊中间态），
  并把整层"色彩守卫"换成**"中性灰守卫"**：`不要任何色相、不要暖黄、不要偏褐、不要偏蓝、不要滤镜式单色染色、不要在灰阶上叠色调`。
  交付时还要把这一点当作**显式授权**写进提示词正文（"本次是有意去色，其它任何情况下都不得去色"）。
  验收用 `audit_and_check.py check` 的**平均彩度**：实测目标 27.2 → 结果 0.9，去色干净。

## 升级规则：什么时候别再改提示词

同一处失败**连续两轮未解决**时，停止调提示词，按顺序升级：

1. **局部重绘**——只重画出问题的那一小块。
   **可用配方（2026-09-22 实测确定）**：`run_round.py --mask <png> --mask-primary`
   （蒙版里**白／不透明＝要改的区域**）。**两段都要有**：
   · `--mask` 单独用**不会产生编辑**——把干净原图一起送过去时，模型会照抄原图
     把涂红区"恢复"成原样（6 次调用全部返回近原图，蒙版内最大改动仅 41–59）；
   · `--mask-primary`（把涂红图当**主图**发、不发干净原图）才逼出真正的重画——
     实测那只黑色蝴蝶结一次画成，蒙版内改动 >120 的像素占 25%。
   矩阵证据（同蒙版、同提示词、只换一个变量）：`--pad pad` ✗、可改面积放大到 16.5% ✗、
   **`--mask-primary` ✓**，且 **2/2 复现**（两次都画出要求的黑色蝴蝶结）。
   **两个代价必须知道**：
   ① 整图会被**轻微微调**（均值约 5/255，不是逐像素保护）——要"逐像素证明保护区没动"才用不带
   `--mask-primary` 的旧配置（那是它唯一还有用的场合）；
   ② 体积：不加 primary 时发两张全尺寸图且不走压缩梯子，**超 1.96 MiB 直接拒发**
   （1536×1024 = 2.15 MiB → HTTP 400）；加了 primary 只发一张，**2048×1152 = 1.29 MiB 也能发**。
   附带事实：加了 primary 的两次都走了 **`b64` 响应路线并返回 1254×1254**（请求是 1024×1024）——
   **`b64` 路线不遵守 `size`**（台账里 `url` 路线全部精确命中）。而"改得动"到底来自
   "抽掉干净原图"还是"这条路线的后端不同"**尚未完全分离**（最早那次 3 图载荷也在该路线上、却没改动，
   故倾向前者）。
   发送前会打印"涂红图已落盘"（`work/*.redmark.png`）——**先看一眼红色落在哪一块**，
   落错位置等于白跑一次调用（实测踩过）。
   **反向用法 `--mask-invert`**（蒙版里涂过的区域**被保留**、其余整张可改）：
   保护这半是实测有效的，**用它时不要加 `--mask-primary`**（保护正是它的目的）。
   适合「保住脸／身份像素不动，只重画服装、姿态或背景」（涂脸＝保脸）。
   三点注意：① 可改面积通常 >80%，等于整图重绘；② **保护区是原像素硬贴**，整体换色会在新画面上留下
   **硬边色块**（实测图见 `round_snow/work/_zoom_mask_face.png`），所以**不能用来做整体调色**；
   ③ 命令会打印可改面积并在 >60% 时警告。

2. **两段式**——先只做姿态（不投风格图、删掉 STYLE 段），姿态定稿后再拿结果做风格迁移。
3. **换模型通道**——单图任务可用 `--model grok-imagine-edit`。2026-10-06 实测：向 Grok edits 同时发送 `image` 与 `image[1]` 返回 HTTP 400。双图任务改走 `gpt-image-2.5-sunburst`，不得拼接应付。
   ⚠ **两段式已废弃（2026-10-06 用户判定「一点也不好」）**：t2i 先画构图再贴画风会丢参考图的画风灵魂——画风活在像素里，第一段没有像素、第二段救不回来，产出通用平涂。同风格新构图改走**裁片引导**（投喂图一局部裁片，模型补全新背景，画风像素原生）或镜像底图。
4. **确定性问题不要生成**——改浓淡／放大／裁切／拼版走本地像素处理（见开工四问第 0 条）。

理由：小结构（手、细链、小饰品）的保真度存在**纯文本给不出的天花板**。

**补充判据——"几何互斥"型失败**：如果两个要求在几何上争同一块面积（例如"眼睛闭成月牙"与"看得见瞳孔"、"手在胸前交握"与"手里拿着东西"），
那么模型只会在两个稳定解之间跳，加形容词最多把结果从一头推到另一头，**永远拿不到中间解**。
识别信号：连续两轮的失败**方向相反**（一次太收、一次太放）。此时不要再调词——按第 2、3 条升级（两段式／换通道），
小结构画错则走第 1 条（`--mask --mask-primary` 局部重绘）。历史记录里手势这一步来回烧了 6 轮，最后是"输入图预处理 + 具体失败态负向"才解决，而不是继续加形容词。

**第三条判据——「表情会连带改比例」**：夸张表情（张嘴大笑、大叫、惊讶）会**连带把眼睛放大、脸颊推圆**，
即在这类模型里「表情」与「脸型比例」**不是正交的**。
凡要「像某个具体角色」的活，**表情要挑不触发夸张的那些**。
（实测：同一份提示词只把「闭嘴微笑露虎牙」改成「张嘴大笑」，那一格的脸就明显比另两格幼；
且靠「眼睛不要张大」这类指令**压不住**——只部分生效，**换表情比调词有效**。）

## 改图前必查的两件事

1. **参考图与目标图是不是同一个文件**（哈希比对）。历史上出现过二者哈希相同，等于自我迁移，白干一整轮。
2. **要消失的元素是否已被物理抹掉**。抹完还要看擦除区有没有留下"与某个身体部位同色的平滑补丁"——有的话必须降色度并往背景色拉（`scripts/erase_region.py` 的 `--neutralize` 选项自带），否则会被模型当成身体部位继续画下去。

## 验证纪律：能出数的就不要靠肉眼

实测规律（本轮全程验证）：**凡是我用肉眼下结论的地方，后面几乎都返工**——
读网格坐标连错 3 次、把三联缩略图的压缩伪影当成「字幕没擦掉」、把「太死板」误判成版式问题（实际是面部不像）。
**凡是用脚本出数的地方一次就对**——彩度、纸白占比、调子剖面、改动范围逐字节证明。
所以每轮判断前先问一句：**「这个判断能不能变成一条命令？」**

**混合验收（2026-10-06 起）**：能出数的（彩度／色相漂移／留白／尺寸）用 `audit_and_check.py check` 出数；
出不了数的（身份像不像、发饰在不在、参考泄漏有没有）**逐项人工打勾并写明「人工」**，
不许拿脚本数字冒充身份验收，也不许把「文件已保存」当成语义通过。

**验收三条红线（2026-10-06 樱花系列事故后补）**：
1. **验收必须描述「实际看到的画面」**——发现描述与生成预期不符＝红灯，先停下查文件再继续。
   （实测：发丝修复版验收时把初版构图当成修复版来描述，三个真实问题全部漏检。）
2. **用户指认多个问题时，逐个裁片确认再合并蒙版一次修**——多块矩形一次 POST，别一个问题一轮。
   （实测：斑点／面部扭曲／眼遮蔽三问题一蒙版（35.8%）一次全修。）
3. **局部重绘后必须检查邻区连带**（遮挡关系／亮度／结构衔接），出问题只报不擅自修。

**修复循环失控熔断（2026-10-06 樱花系列四连败后定稿）**：同一张图连续两轮修复后**仍出现新问题**——
立即停止修复，回滚到**上一个被用户认可的版本**，向用户报告循环并重新评估路线（换路线／放弃／重来），
**不得发起第三轮修复**。实测：樱花版四连修（乱线圈→脸崩→AI 味→全图重诠释）一轮比一轮差，
每轮验收还都在自报成功——修复不是免费的重掷，每次都在累积新的随机退化。

**已知缺口（待补，如实标注）**：面部与体格的比例（头身比、肩宽:头宽、眼高:脸高）**目前没有可靠量法**。
`round_lib/body_report.py` 的轮廓法实测失效（曾把 R1 量成 11.8 头身、把腰误判成颈）；
2026-09-22 已加两道闸——**人物被切到时一律不报数**、**超出 2.5–10 合理区间不报数**（只打「—」并给理由），
所以现在它不会再把 11.8 这种读数交出来了，但**仍然只能当参考**：
网格目测误差约 **±1 头身**，判不出 6.3 与 7.1 的差别。这一处只能靠人眼判，并如实说明。

**同族缺口——脸部「去 AI 味」文字对抗已证伪（2026-10-07）**：局部重绘时用文字要求「水彩质感／手绘感」
会让模型**加更多渲染细节**（越描越 AI）；有效手段只有两个——**双图参考修复**（image[1]=画风参考，
重绘幅度大、适合大修）或**一次生成到位**（低细节闭眼/侧影脸不触发渲染倾向）。
经验：图一式五官本就是低细节水彩色块，追求「精致虹膜＋高光」恰恰是 AI 味的来源。

## 改源码必须编译校验

**规则**：
· **新增或修改任何 `.py`，执行前先 `compile()`**——"新建"与"修改"同等对待
  （实测：我在**新建**一个脚本时把 UTF-8 前置写在 `from __future__` 之前，同一个错犯了第三次）；
· 改动已有源码的补丁，**写回前必须 `compile()` 校验通过**（不过关就不写），改完**再全量编译复核一次**；
· 批量删除／替换还要先**干跑打印**给人看。

**依据（本会话事故）**：我用补丁给 6 个脚本插入一段 UTF-8 前置，插入点选在"第一个 import 之前"——
而这些文件的第一个 import 是 `from __future__ import annotations`，**它必须是文件的第一条语句**，
于是 **6 个脚本全部 `SyntaxError`，工具链当场全坏**。第一版补丁**既没干跑、也没写后校验**；
修正版加了"写回前 compile、改完全量复核"，6 个脚本立刻恢复。

对照：那次批量删除脚本靠**干跑**拦下了一次真实误删（它本会删掉 3 行无关表格与一整段与目标无关的正文）。
**两次事故、两种校验——缺一个就出一次事。**

## 作业纪律：命令一律写成脚本文件，不内联

**规则**：**超过一行的命令**（尤其是含中文、含引号、含多步逻辑的），
**一律先写成 `.py` 或 `.sh` 文件再执行**，不要内联拼进 shell。

**这条纪律覆盖「脚本文件内部」，不只覆盖命令行**（落地之后才发现的漏洞：写下这条规则之后，
本会话仍因**脚本内部**的问题失败 2 次，其中一次正是"用 ASCII 直引号包中文"）：
1. **无论是内联命令还是脚本文件内部，都禁止用 ASCII 直引号包中文**——一律「」或中文引号；
2. **跨行字符串不要漏写闭合引号**（也实测犯过）；
3. **不要凭记忆写 shell 语法**：`<` 重定向在 PowerShell 里**不存在**（只能 `cmd /c "… < nul"`）；
   不存在的 cmdlet（如 `Get-TempFileName`）与 `@args` 展开写法会**静默失败**。

**依据（本项目实测）**：本会话因**内联拼命令**失败 **≥4 次**，成因全是引号层级——
嵌套双引号、单引号套单引号、反斜杠转义引号，另有中文引号被 shell 吃掉。
而**写成文件之后失败 0 次**（`make_v13.py`、那次逐处精准删除脚本、`patch_skill_v3.py`、`patch_ops_and_dryrun.py`
全部一次通过）。〔2026-09-25 核对：这四个里只有 `patch_ops_and_dryrun.py` 已不在库中（它原本只是备份目录里的
一份副本，该目录已随清理移除）；`make_v13.py` 现在 `round_manga/scripts/` 下。此处保留的是那笔实测记录本身。〕

**附带收益**：脚本**可复现、可重跑、可干跑**。
那次批量删除脚本就是靠"先干跑打印"才发现它会**误删不相关的表格行与整段正文**
（"删对了关键词、删错了范围"）——内联命令根本没法这样自查。

判据一句话：**命令里出现第二个引号层级、或者出现中文，就不要再内联了。**

## 怎么持续优化这个 skill

1. 每轮结束后，往 `LESSONS.md` 追加一条：现象 → 根因 → 有效动作 → 是否可复用。
2. 可复用的失败形态加进 `references/negative-library.md`；新的泄漏特征加进 `references/identity-library.md`。
3. 接口行为变化（尺寸、字段、限额）写进 `references/pipeline-notes.md`，并注明实测日期。
4. **判断一条经验该不该进 skill 的标准**：它是否改变了"下一次的动作"。只描述现象的观察记进 LESSONS 就够，不要写进 SKILL.md 的主流程。
5. **改完必须同步**：运行时副本在 `~/.agents/skills/style-distill/`，仓库镜像在 `style-distill/_skill/style-distill/`。
   每次修改仓库镜像后，把 SKILL.md／LESSONS.md／references/ 整体复制过去并逐字节比对
   （实测 2026-10-06：只改一边导致运行时读旧账本，Grok 双图教训在下一轮丢失）。
