# 执行技术 policy

这是 image-edit 的按需技术参考，不是生成授权。所有数值都属于特定 relay/日期的观测，不能当作普世上限；当前环境必须重新 dry-run 或离网检查。

## 路由与提交

- 先判断能否用 `zimage.py local` 确定性完成；能完成就不调用上游。
- `doctor` → 本地 plan/dry-run → 人工检查角色、区域、redmark、比例和预算 → 唯一 owner 一次 POST。
- `prompt_only`、inspect、gallery、dry-run 均不 POST；受理状态未知时停止，不自动重试。
- 凭据只读 `RELAY_API_KEY`、`RELAY_BASE_URL`、`RELAY_MODEL`，不写日志、计划或仓库。

## 局部 mask

- 正向“涂哪改哪”通常使用 `--mask-primary`；它会移除干净原图的复原诱因，但不是逐像素保护，整图可能轻微变化。
- 反向“涂哪保哪”使用 `--protect`/反向 mask，不配 `--mask-primary`。它是模型约束，不是确定性像素合成；必须用保护区 metrics 和语义 review 验证，因此不用于整体调色。
- 涂红会清掉目标区原信息，只适合该区本来就要重画。保留细节、只改明度或上色时优先整图约束或本地操作。
- `mask` 表单是否被中转站采用、redmark 语义和任意形状支持都要按当前工具链核实，不能只凭历史 HTTP 200。

## 体积、尺寸、下载

历史 relay 观测曾见约 1.96 MiB 门槛、JPEG 比 PNG 小约 5 倍、b64 返回尺寸偏离请求、CDN 速度大幅抖动。这些只用于解释旧记录，不是默认硬编码策略。目标尺寸白名单、编码格式、下载工具和超时必须以当前 `doctor`/dry-run/离网测试输出为准。

结果拿到 URL/id 后先登记，再取回；下载完成要 `Image.open(...).load()` 完整解码并核对实际尺寸。不要把 retry 502 写成普遍恢复保证；不自动重发一个受理状态未知的请求。

## 语义验收

技术通过条件：文件可解码、实际尺寸/字节有记录、任务需要的局部改动范围有数据。语义通过条件：逐项核对用户点名的变化、身份保持、参考泄漏、构图/遮挡和邻区连带。标签重合率、文件存在、HTTP 200 或尺寸正确都不能独立放行。

结论标注 `【实测】`、`【文件核实】`、`【判断】`、`【未验证】`。对于物理硬贴、b64 行为、当前 Grok 恢复/fallback 和 retry 502，若本次未测，明确标为未验证。
